# URL 介绍

**统一资源定位符**（Uniform Resource Locator，缩写：**URL**，或称统一资源定位器、定位地址、URL地址），俗称网页地址，简称**网址**，是因特网上标准的资源的地址（Address），如同在网络上的门牌。

它最初是由蒂姆·伯纳斯-李发明用来作为万维网的地址，现在它已经被万维网联盟编制为因特网标准RFC 1738。

>URL 就是统一资源定位符，简称网址，用于访问网站上的资源。

## 本质定义

URL（Uniform Resource Locator）是用于完整描述互联网上资源位置与访问方式的标准化字符串。

- 核心本质

  它不仅仅是一个“地址”，更是一套**寻址指令**。它告诉客户端（如浏览器）使用什么协议、去哪里找服务器、端口是多少、以及具体要获取哪个资源。

- 所属体系

  URL 是 URI（统一资源标识符）的一个子集。URI 负责“标识”资源（我是谁），而 URL 负责“定位”资源（我在哪，怎么找到我）。

## 标准语法结构

一个完整的 URL 遵循以下标准格式（方括号内为可选部分）：

```text
<协议>://<用户名>:<密码>@<主机>:<端口>/<路径>?<查询参数>#<片段标识符>
```

| 语法成分                  | 作用描述                         | 典型示例与说明                                               |
| ------------------------- | -------------------------------- | ------------------------------------------------------------ |
| **协议（Scheme）**         | 指定访问资源所使用的应用层协议   | `http`、`https`、`ftp`、`file`。<br />决定了客户端与服务器通信的规则。 |
| **主机（Host）**           | 指定资源所在的服务器位置         | 域名（如 `www.example.com`）或 IP 地址（如 `192.168.1.1`）。 |
| **端口（Port）**           | 指定服务器上监听请求的具体端口号 | 如 `:8080`。<br />若省略，则使用协议的默认端口<br />（HTTP 默认为 80，HTTPS 默认为 443）。 |
| **路径（Path）**           | 指定服务器上资源的具体层级位置   | 如 `/api/v1/users`。<br />类似于文件系统中的目录结构。       |
| **查询参数（Query）**      | 向服务器传递额外的键值对数据     | 以 `?` 开头，多个参数用 `&` 连接（如 `?id=123&type=active`）。 |
| **片段标识符（Fragment）** | 指定资源内部的某个锚点或片段     | 以 `#` 开头（如 `#section1`）。<br />**片段不会发送给服务器**，仅由浏览器本地处理。 |
| **用户信息（UserInfo）**   | 用于身份验证的用户名和密码       | 如 `admin:123456@`。<br />出于安全考虑，现代浏览器已极少在 URL 中明文传递密码。 |

*http 协议：超文本传输协议。*

## URL 与 URI 的核心区别

1. URI（Uniform Resource Identifier）

   统一资源标识符。它是一个更广泛的概念，用于唯一标识一个资源。

2. URL（Uniform Resource Locator）

   统一资源定位符。它是 URI 的一种具体实现，不仅标识资源，还提供了**定位和访问**该资源的方法。

3. 关系

   所有的 URL 都是 URI，但并非所有的 URI 都是 URL（例如 URN 统一资源名称，只负责命名不负责定位）。

## 编码机制

Percent-Encoding。

URL 标准规定，URL 中只能包含有限的 ASCII 字符（字母、数字及少量特殊符号）。

- 编码规则

  对于非 ASCII 字符（如中文）或保留字符（如空格、`&`、`=`），必须使用 `%` 加上该字符的十六进制 ASCII 码进行替换。

- 示例

  空格会被编码为 `%20`，中文字符“中”会被编码为 `%E4%B8%AD`。

- 作用

  确保 URL 在传输过程中不会因为特殊字符导致解析错误或协议冲突。

## URL 在计算机网络中的工作流

当在浏览器中输入一个 URL 并回车时，底层会触发一系列网络请求：

1. **解析协议与主机**：浏览器提取协议和域名。
2. **DNS 解析**：将域名转换为服务器的 IP 地址。
3. **建立连接**：根据端口号，与服务器建立 TCP 连接（若是 HTTPS 还需进行 TLS 握手）。
4. **发送请求**：浏览器按照指定协议（如 HTTP）向该 IP 和端口发送请求报文，报文中包含路径和查询参数。
5. **接收响应**：服务器处理请求后返回资源数据，浏览器进行渲染或下载。

## 安全性

- HTTPS 优先

  在生产环境中，应始终使用 `https` 协议，以防止 URL 中的敏感信息（如查询参数中的 Token）被中间人窃听或篡改。

- 避免敏感信息泄露

  切勿在 URL 的查询参数中传递密码、密钥或会话 ID，因为 URL 会被记录在浏览器历史、服务器日志和代理服务器中。

- RESTful 规范

  在现代 Web 开发中，URL 的设计通常遵循 RESTful 风格，将资源名词作为路径（如 `/users/123`），将操作动词映射为 HTTP 方法（如 GET、POST），使 URL 具备自描述性。

# 查询参数

## 定义

查询参数（Query Parameters），又称查询字符串（Query String），是附加在 URL 路径（Path）之后的一组键值对数据。

- 核心本质

  它是客户端向服务器传递**附加信息**或**过滤条件**的标准机制。服务器通过解析这些参数，动态地定制返回内容或执行特定操作，而无需为每种情况创建独立的 URL 路径。

- 语法位置

  查询参数位于 URL 的问号（`?`）之后，片段标识符（`#`）之前。

## 标准语法结构

查询参数遵循严格的键值对（Key-Value Pair）格式：

```text
?key1=value1&key2=value2&key3=value3
```

| 语法成分    | 作用描述               | 示例与说明                                              |
| ----------- | ---------------------- | ------------------------------------------------------- |
| `?`         | 查询字符串的起始分隔符 | 标志着 URL 路径的结束和查询参数的开始。                 |
| `key=value` | 单个参数的键值对       | `key` 为参数名，`value` 为参数值，中间用等号 `=` 连接。 |
| `&`         | 参数间的连接符         | 用于分隔多个独立的键值对。                              |

## 核心作用

| 作用维度           | 详细说明                                       | 典型示例                                                |
| ------------------ | ---------------------------------------------- | ------------------------------------------------------- |
| **数据过滤与筛选** | 告诉服务器仅返回符合特定条件的数据子集。       | `?category=books&author=twain`（仅返回马克·吐温的书籍） |
| **内容排序**       | 指定返回数据的排序规则。                       | `?sort=price&order=asc`（按价格升序排列）               |
| **分页控制**       | 在大数据集中指定当前请求的数据页码和每页数量。 | `?page=2&limit=20`（获取第 2 页，每页 20 条）           |
| **搜索功能**       | 传递用户的搜索关键词。                         | `?q=typescript+tutorial`（搜索 TypeScript 教程）        |
| **状态追踪**       | 记录用户的操作状态或偏好设置。                 | `?lang=zh-CN&theme=dark`（设置中文界面和深色主题）      |
| **营销追踪**       | 追踪广告来源、媒介及活动名称（UTM 参数）。     | `?utm_source=google&utm_medium=cpc`                     |

## 前后端使用方式

### 前端构建与解析

1. 构建参数

   使用 `URLSearchParams` API 可以安全地构建查询字符串，自动处理特殊字符的编码。

   ```js
   const params = new URLSearchParams();
   params.append('page', '1');
   params.append('limit', '10');
   const queryString = params.toString(); // 输出: "page=1&limit=10"
   ```

2. 解析参数

    从当前页面 URL 中提取参数值。

    ```javascript
    const urlParams = new URLSearchParams(window.location.search);
    const page = urlParams.get('page'); // 获取 'page' 参数的值
    ```

### 后端接收与处理

后端框架（如 Node.js 的 Express、Python 的 Flask）会自动解析 URL 中的查询字符串，并将其映射为请求对象上的属性（如 `req.query`）。

后端根据解析出的键值对执行相应的业务逻辑（如拼接 SQL 查询语句、调用外部 API 等）。

## 注意事项

1. URL 编码（Percent-Encoding）

   如果参数值中包含特殊字符（如空格、`&`、`=`、中文等），必须进行 URL 编码。例如，空格应被编码为 `%20` 或 `+`。

2. 安全性限制

   **严禁**在查询参数中传递敏感信息（如密码、Token、身份证号）。因为 URL 会被明文记录在浏览器历史、服务器日志、代理服务器以及 Referer 请求头中，极易造成数据泄露。

3. 长度限制

   虽然 HTTP 协议本身未限制 URL 长度，但浏览器和服务器通常有上限（如 IE 限制为 2083 字符，现代浏览器通常支持 8000+ 字符）。过长的参数应考虑使用 POST 请求体传递。

4. SEO 影响

   大量重复或无意义的查询参数可能导致搜索引擎抓取到大量内容相似的页面（重复内容问题），稀释主页面的权重。通常建议使用 `rel="canonical"` 标签或 `robots.txt` 来规范搜索引擎的抓取行为。

5. 与路径参数（Path Params）的区别

   - 路径参数（如 `/users/123`）

     用于标识**具体资源**，是 RESTful API 设计的一部分，具有明确的层级语义。

   - 查询参数（如 `/users?id=123`）

     用于对资源集合进行**过滤、排序或分页**，属于非层级化的附加信息。

# 请求方法

## 定义

请求方法（Request Methods），有时也被称为 HTTP 动词（HTTP Verbs），是 HTTP 协议定义的一组用于指示要对给定资源执行的操作的指令。

1. 核心本质

   请求方法指明了客户端希望服务器针对特定资源执行的具体动作（如获取、创建、更新或删除）。

2. 位置

   请求方法位于 HTTP 请求报文的第一行（请求行）中，紧随其后的是请求的 URL 和 HTTP 协议版本。

## 作用

1. 语义化操作

   通过不同的方法名，清晰地表达客户端的意图，使资源的状态转移更加直观。

2. 实现 RESTful 架构

   在 RESTful API 设计中，请求方法直接映射到数据库的 CRUD（创建、读取、更新、删除）操作，使接口设计更加规范和统一。

3. 控制行为特性

   不同的请求方法具有不同的安全性、幂等性和可缓存性，服务器和浏览器会根据这些特性采取不同的处理策略（如缓存机制、重试机制）。

## 常用请求方法

| 方法       | 核心作用                                                     | 数据位置                     | 典型场景                                 |
| ---------- | ------------------------------------------------------------ | ---------------------------- | ---------------------------------------- |
| **GET**    | 请求获取指定资源的表示形式（只读操作）。                     | URL 查询参数（Query String） | 获取用户列表、搜索商品、获取文章详情。   |
| **POST**   | 向服务器提交数据，通常用于创建新资源或触发副作用。           | 请求体（Request Body）       | 用户注册、提交表单、上传文件、创建订单。 |
| **PUT**    | 用请求体中的完整数据替换目标资源的所有当前表示（全量更新）。 | 请求体（Request Body）       | 修改用户的所有信息（需提供完整字段）。   |
| **DELETE** | 删除指定的资源。                                             | URL 路径（标识资源）         | 删除用户账户、取消订单、移除购物车商品。 |
| **PATCH**  | 对资源应用部分修改（增量更新）。                             | 请求体（Request Body）       | 仅修改用户的邮箱或密码，不改变其他字段。 |

## 特性

| 方法       | 安全性 (Safe)            | 幂等性 (Idempotent)                  | 可缓存性 (Cacheable)           |
| ---------- | ------------------------ | ------------------------------------ | ------------------------------ |
| **GET**    | 是（不修改服务器状态）   | 是（多次请求结果相同）               | 是（可被浏览器或 CDN 缓存）    |
| **HEAD**   | 是                       | 是                                   | 是                             |
| **POST**   | 否（可能修改服务器状态） | 否（多次提交可能创建多个资源）       | 条件可缓存（需响应头明确指示） |
| **PUT**    | 否                       | 是（多次更新同一资源，最终状态一致） | 否                             |
| **DELETE** | 否                       | 是（多次删除同一资源，最终状态一致） | 否                             |
| **PATCH**  | 否                       | 否（部分更新可能因并发导致不同结果） | 条件可缓存                     |

1. 安全性

   指该方法不会修改服务器上的资源状态。GET 和 HEAD 是安全的。

2. 幂等性

   指无论执行多少次相同的请求，其对服务器资源产生的影响都是相同的。GET、PUT、DELETE 是幂等的。

3. 可缓存性

   指该请求的响应是否可以被浏览器或中间代理服务器缓存。

## RestFul 风范

| 请求方法 | 操作             |
| -------- | ---------------- |
| GET      | 获取数据         |
| POST     | 提交数据         |
| PUT      | 修改数据（全部） |
| DELETE   | 删除数据         |
| PATCH    | 修改数据（部分） |

## 其他辅助请求方法

| 方法        | 作用描述                                                     |
| ----------- | ------------------------------------------------------------ |
| **HEAD**    | 与 GET 请求类似，但服务器只返回响应头，不返回响应体。常用于获取资源的元数据（如文件大小、修改时间）或检查资源是否存在。 |
| **OPTIONS** | 用于获取目标资源支持的通信选项（如允许的请求方法）。常用于跨域请求（CORS）前的预检（Preflight）请求。 |
| **CONNECT** | 建立一个到由目标资源标识的服务器的隧道，通常用于 SSL/TLS 加密通信（HTTPS）。 |
| **TRACE**   | 沿着到目标资源的路径执行一个消息环回测试，用于诊断网络连接问题。 |

## 代码示例

### Python

```python
import requests

# GET 请求：获取资源
response = requests.get('https://api.example.com/users/1')

# POST 请求：创建资源
data = {'name': 'Alice', 'age': 25}
response = requests.post('https://api.example.com/users', json=data)

# PUT 请求：全量更新资源
update_data = {'name': 'Alice', 'age': 26, 'email': 'alice@example.com'}
response = requests.put('https://api.example.com/users/1', json=update_data)

# DELETE 请求：删除资源
response = requests.delete('https://api.example.com/users/1')
```

### JS

```js
// 定义需要提交的新用户数据
const newUser = {
  name: 'Alice',
  age: 25
};

// 发起 POST 请求创建新用户
fetch('https://api.example.com/users', {
  method: 'POST', // 指定请求方法为 POST
  headers: {
    'Content-Type': 'application/json' // 声明请求体的数据格式为 JSON
  },
  body: JSON.stringify(newUser) // 将 JS 对象序列化为 JSON 字符串并放入请求体
})
  .then(response => response.json())
  .then(data => console.log('创建成功:', data))
  .catch(error => console.error('创建失败:', error));
```

# 请求报文

请求行、请求头和请求体共同构成了完整的 HTTP 请求报文。它们属于计算机网络协议栈中的**应用层协议（HTTP 协议）知识**，是理解前后端数据交互、网络通信原理以及 Web 开发底层逻辑的核心基础。

- HTTP 协议

  规定了浏览器发送及服务器返回内容的格式。

- 请求报文

  浏览器按 HTTP 协议要求的格式，发送给服务器的内容。

> 在浏览器检查元素的网络中可以看到请求报文。

## 请求行

请求行（Request Line）是 HTTP 请求报文的第一行，主要用于向服务器声明客户端的核心意图，即“要做什么”以及“要访问哪个资源”。

请求行由三个核心元素组成，中间以空格分隔，并以回车换行符（`\r\n`）结束。

```http
POST /api/users HTTP/1.1
```

| 语法成分  | 作用描述                                 | 可选值或数据类型                           |
| --------- | ---------------------------------------- | ------------------------------------------ |
| 请求方法  | 指定对资源执行的具体操作类型             | `GET`、`POST`、`PUT`、`DELETE`、`PATCH` 等 |
| 请求 URI  | 标识请求的目标资源路径（可包含查询参数） | 字符串（如 `/api/users?id=1`）             |
| HTTP 版本 | 声明客户端使用的 HTTP 协议规范版本       | `HTTP/1.1`、`HTTP/2.0` 等                  |

## 请求头

请求头（Request Headers）紧随请求行之后，由多个键值对（Key: Value）组成。其核心作用是提供关于请求的补充元数据，告知服务器客户端的环境信息、身份凭证以及对响应内容的偏好。

**常见请求头字段详解**

```http
HOST: www.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
```

| 语法成分         | 作用描述                                | 可选值或数据类型                                             |
| ---------------- | --------------------------------------- | ------------------------------------------------------------ |
| Host             | 指定请求的目标服务器域名及端口号        | 字符串（如 `www.example.com:8080`）                          |
| **Content-Type** | 声明请求体中数据的媒体格式（MIME 类型） | `application/json`、<br />`application/x-www-form-urlencoded`、<br />`multipart/form-data` |
| Authorization    | 携带用于身份验证的凭据或令牌            | 字符串<br />（如 `Bearer <token>`、`Basic <credentials>`）   |
| User-Agent       | 标识发起请求的客户端软件及操作系统信息  | 字符串（浏览器或 HTTP 客户端库的标识串）                     |
| Accept           | 声明客户端能够接收和处理的响应内容类型  | 字符串（如 `application/json, text/plain`）                  |

## 请求体

请求体（Request Body）位于请求头之后，两者之间必须用一个空行（`\r\n\r\n`）进行分隔。请求体用于携带客户端向服务器发送的**实际业务数据**，通常出现在 `POST`、`PUT`、`PATCH` 等需要提交数据的请求方法中，`GET` 请求通常不包含请求体。

**常见数据格式与构建方式**

请求体的具体格式完全由请求头中的 `Content-Type` 字段决定。

```javascript
// 以 JSON 格式构建请求体为例
const requestBody = JSON.stringify({ username: "alice", age: 25 });
```

| 语法成分   | 作用描述                                      | 可选值或数据类型                            |
| ---------- | --------------------------------------------- | ------------------------------------------- |
| JSON 数据  | 传输结构化的业务数据，现代 API 交互的主流格式 | 字符串（需通过 `JSON.stringify()` 序列化）  |
| 表单数据   | 传输传统的键值对参数，常用于简单表单提交      | 字符串（如 `username=alice&age=25`）        |
| 二进制数据 | 传输文件或混合数据，专用于文件上传场景        | `FormData` 对象（浏览器自动处理边界字符串） |

## 完整报文结构示例

以下是一个标准的 HTTP POST 请求报文，清晰展示了三者的层级关系：

```http
POST /api/users HTTP/1.1
Host: www.example.com
Content-Type: application/json
Content-Length: 35
Authorization: Bearer token123

{"username":"alice","age":25}
```

1. 第一行

   请求行（声明使用 POST 方法访问 `/api/users`）。

2. 中间部分

   请求头（声明主机、数据格式、数据长度及身份令牌）。

3. 空行

   分隔符（告知服务器头部信息已结束）。

4. 最后一行

   请求体（实际传输的用户业务数据）。

# 请求数据格式

请求数据格式（Content-Type）由 HTTP 请求头中的 `Content-Type` 字段决定。该字段告知服务器如何解析请求体（Body）中的数据。不同的数据格式对应不同的序列化方式与适用场景。

## 数据格式详解

### JSON 格式

application/json，现代前后端交互中最主流的数据交换格式。数据以键值对的形式组织，结构清晰且易于解析。

- 语法特征

  使用花括号 `{}` 包裹对象，键名必须使用双引号，支持嵌套数组与对象。

- 适用场景

  RESTful API 交互、复杂数据结构传输、前后端分离项目。

- 序列化方式

  在 JavaScript 中需使用 `JSON.stringify()` 将对象转换为 JSON 字符串。

```json
{
  "username": "alice",
  "age": 25,
  "roles": ["admin", "editor"]
}
```

### 表单格式

application/x-www-form-urlencoded，HTML 表单的默认提交格式。数据被编码为键值对，多个参数之间使用 `&` 连接，特殊字符会被 URL 编码。

- 语法特征

  `key1=value1&key2=value2`。

- 适用场景

  传统的 HTML 表单提交、简单的键值对数据传递。

- 序列化方式

  在 JavaScript 中可使用 `URLSearchParams` 对象自动处理编码。

```text
username=alice&age=25&role=admin
```

### 多部分表单格式

multipart/form-data，专为文件上传设计的格式。它将表单数据分割为多个部分（Part），每个部分可以包含不同的内容类型（如文本、图片、视频）。

- 语法特征

  使用边界字符串（Boundary）分隔不同的数据块，支持二进制流传输。

- 适用场景

  文件上传、包含二进制数据的表单提交。

- 序列化方式

  在 JavaScript 中必须使用 `FormData` 对象构建，浏览器会自动添加正确的边界字符串。

```text
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="username"

alice
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="avatar"; filename="photo.png"
Content-Type: image/png

[二进制文件数据]
------WebKitFormBoundary7MA4YWxkTrZu0gW--
```

### 纯文本格式

text/plain，最基础的格式，数据以纯文本字符串形式传输，不进行任何结构化解析。

- 适用场景：日志上传、简单的字符串消息传递。

## 格式对比

| 数据格式       | Content-Type 值                     | 核心优势                           | 典型应用场景                    |
| -------------- | ----------------------------------- | ---------------------------------- | ------------------------------- |
| **JSON**       | `application/json`                  | 结构清晰、支持嵌套、跨语言兼容性好 | 现代 API 交互、复杂业务数据传输 |
| **表单**       | `application/x-www-form-urlencoded` | 兼容传统后端、浏览器原生支持       | 传统表单提交、简单参数传递      |
| **多部分表单** | `multipart/form-data`               | 支持二进制文件、可混合文本与文件   | 文件上传、头像修改、附件发送    |
| **纯文本**     | `text/plain`                        | 无额外开销、传输轻量               | 日志上报、简单消息推送          |

## JS 中的发送方式对照

| 数据格式       | 构建方式                    | 请求头设置                                                   |
| -------------- | --------------------------- | ------------------------------------------------------------ |
| **JSON**       | `JSON.stringify(data)`      | `headers: { 'Content-Type': 'application/json' }`            |
| **表单**       | `new URLSearchParams(data)` | `headers: { 'Content-Type': 'application/x-www-form-urlencoded' }` |
| **多部分表单** | `new FormData()`            | **无需手动设置**（浏览器会自动添加 Boundary）                |
| **纯文本**     | 直接使用字符串              | `headers: { 'Content-Type': 'text/plain' }`                  |

## 注意事项

1. 优先使用 JSON

   在现代 Web 开发中，除非涉及文件上传或兼容旧系统，否则应优先选择 JSON 格式。

2. 文件上传必须用 FormData

   `multipart/form-data` 是唯一支持二进制文件上传的标准格式，切勿尝试将文件转为 Base64 放入 JSON 中（会导致数据体积膨胀约 33%）。

3. 注意编码问题

   使用 `application/x-www-form-urlencoded` 时，若参数值包含中文或特殊字符，务必确保正确进行 URL 编码。

4. 后端解析匹配

   请求头的 `Content-Type` 必须与服务端的解析逻辑一致，否则服务端将无法正确读取数据（如发送 JSON 但服务端按表单解析，会导致数据丢失）。

# 请求报文与 URL 的关系

请求报文（Request Message）与 URL（统一资源定位符）是“整体与局部”、“载体与内容”的关系。URL 是请求报文中用于定位资源的核心组成部分，而请求报文是承载并传输该 URL 的完整通信载体。

## 核心关系

- URL 是请求报文的子集

  一个完整的 HTTP 请求报文由请求行、请求头和请求体三部分组成。URL 并非独立存在，而是被拆解并嵌入到了请求报文的**请求行**中。

- 请求报文是 URL 的传输载体

  URL 本身只是一串字符，必须依附于 HTTP 请求报文，才能被浏览器或客户端发送给服务器，从而触发实际的网络通信。

## URL 在请求报文中的位置

在标准的 HTTP 请求报文中，URL 主要出现在以下位置：

### 请求行

这是 URL 最核心的存在位置。请求行中的“请求 URI”字段，实际上就是 URL 中的**路径（Path）**和**查询参数（Query）**部分。

```http
GET /api/users?page=1&limit=10 HTTP/1.1
```

- `/api/users?page=1&limit=10` 即为 URL 的路径与查询参数部分。

### 请求头

URL 中的**主机（Host）**部分，通常会被单独提取出来，放入请求头的 `Host` 字段中。

```http
Host: www.example.com
```

- 这种拆分是为了让服务器能够准确识别虚拟主机（即同一 IP 下托管的多个域名）。

## 功能维度的区别与联系

| 对比维度     | URL（统一资源定位符）                      | 请求报文（HTTP Request）                                     |
| ------------ | ------------------------------------------ | ------------------------------------------------------------ |
| **本质属性** | 资源的“地址”与“访问方式”                   | 客户端与服务器之间的“完整通信数据包”                         |
| **核心作用** | 告诉客户端“去哪里找资源”以及“用什么协议找” | 告诉服务器“要执行什么操作”、“携带什么数据”以及“客户端的身份与环境” |
| **组成结构** | 协议、主机、端口、路径、查询参数、片段     | 请求行（含URL）、请求头、请求体                              |
| **相互关系** | 是请求报文中用于定位资源的关键信息         | 是承载 URL 并补充操作意图、元数据和业务数据的完整载体        |

## 形象化理解

可以将网络请求比作“寄快递”：

- **URL** 相当于快递单上的“收件地址”（省市区街道），它决定了包裹要被送到哪里。
- **请求报文** 相当于整个“快递包裹”，它不仅包含了收件地址（URL），还包含了寄件人信息、包裹内容（请求体）、以及特殊的运输要求（请求头）。

## 总结

URL 解决了“资源在哪里”的问题，而请求报文解决了“如何与服务器进行完整交互”的问题。在实际的网络通信中，浏览器会将用户输入的完整 URL 解析，并将其中的路径和参数放入请求行，将主机名放入请求头，最终组装成一个完整的请求报文发送给服务器。

# 查询参数和请求报文的关系

查询参数与请求报文的关系，可以从**结构层级**和**传输位置**两个维度来理解。查询参数是 URL 的组成部分，而 URL 又是请求报文中请求行的核心内容。因此，查询参数是请求报文中用于传递附加过滤条件或状态信息的嵌套数据块。

## 结构层级关系

> **嵌套包含**

请求报文是一个完整的通信数据包，而查询参数只是其中极小的一部分。它们的层级关系如下：

1. 请求报文

   包含请求行、请求头、请求体。

2. 请求行

   包含请求方法、请求 URI（即 URL 的路径与查询参数部分）、HTTP 版本。

3. URL

   包含协议、主机、路径、查询参数、片段标识符。

4. 查询参数

   URL 中问号（`?`）之后的键值对数据。

## 传输位置关系

> **位于请求行**

在 HTTP 协议的实际传输中，查询参数**不会**被放入请求体（Body）中，而是直接拼接在请求行的 URL 后面，随请求行一起发送给服务器。

**示例说明**

假设前端发起的请求 URL 为 `http://example.com/api/users?page=1&limit=10`，那么生成的 HTTP 请求报文的第一行（请求行）会是：

```http
GET /api/users?page=1&limit=10 HTTP/1.1
```

- `/api/users` 是路径。
- `?page=1&limit=10` 就是查询参数，它直接附着在请求行的 URI 中。

## 功能维度的区别与联系

| 对比维度     | 查询参数 (Query Params)                          | 请求报文 (Request Message)                                   |
| ------------ | ------------------------------------------------ | ------------------------------------------------------------ |
| **本质属性** | URL 中用于传递附加信息的键值对数据               | 客户端与服务器之间完整的通信数据包                           |
| **核心作用** | 对资源进行过滤、排序、分页或传递简单状态         | 承载完整的请求意图，包括操作类型、身份验证、业务数据等       |
| **数据位置** | 位于请求报文的**请求行**（URL 的一部分）         | 包含请求行、请求头、请求体三个完整部分                       |
| **数据容量** | 受限于 URL 长度限制（通常几 KB），不适合传大数据 | 请求体可承载大量数据（如文件上传、复杂 JSON），无严格长度限制 |

## 总结

查询参数是请求报文中**请求行**的一部分。当客户端发起请求时，查询参数会作为 URL 的尾部信息，被直接写入请求报文的起始行中发送给服务器。服务器在解析请求报文时，会首先从请求行中提取出 URL，进而分离出查询参数进行业务处理。

# 响应报文

响应报文（Response Message）是服务器在接收并处理完客户端的请求后，返回给客户端的完整数据包。它属于计算机网络协议栈中的应用层协议（HTTP 协议）知识，是理解前后端数据交互、网络通信原理以及 Web 开发底层逻辑的核心基础。

> 响应报文是服务器按照 HTTP 协议要求的格式返回给浏览器的内容。

## 定义与核心作用

1. 定义

   响应报文是服务器对客户端请求的正式答复。它包含了请求的处理结果、状态信息以及客户端所请求的实际资源或数据。

2. 核心作用

   - 反馈处理结果

     通过状态码和原因短语，明确告知客户端请求是否成功、失败或需要进一步操作。

   - 传输资源数据

     承载客户端请求的实际内容，如 HTML 文档、JSON 数据、图片、视频等。

   - 提供元数据

     通过响应头传递关于响应内容的附加信息，如内容类型、缓存策略、服务器信息等。

   - 管理状态

     通过特定的响应头（如 `Set-Cookie`）在客户端设置会话状态，实现用户登录、购物车等功能的持久化。

## 结构组成

一个标准的 HTTP 响应报文由四个部分组成：状态行、响应头、空行和响应体。

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 45
Cache-Control: no-cache
Server: nginx/1.18.0

{"username":"alice","age":25,"role":"admin"}
```

- 第一行（状态行）

  `HTTP/1.1 200 OK`，表示协议版本为 HTTP/1.1，状态码为 200，原因短语为 OK。

- 中间部分（响应头）

  声明了内容类型为 JSON、内容长度为 45 字节、禁止缓存以及服务器软件信息。

- 空行

  `\r\n\r\n`，用于分隔响应头与响应体。

- 最后一行（响应体）

  实际返回的 JSON 业务数据。

### 状态行

状态行（Status Line）是响应报文的第一行，用于简要说明请求的处理结果。它由三个元素组成，中间以空格分隔。

1. HTTP 版本：服务器使用的 HTTP 协议版本（如 `HTTP/1.1`）。
2. 状态码：一个三位数的数字，表示请求的处理结果（如 `200`、`404`、`500`）。
3. 原因短语：对状态码的简短文本描述（如 `OK`、`Not Found`、`Internal Server Error`）。

```http
HTTP/1.1 200 OK
```

### 响应头

响应头（Response Headers）紧随状态行之后，由多个键值对（Key: Value）组成。其核心作用是提供关于响应内容的元数据，指导客户端如何处理接收到的数据。

| 常见响应头字段   | 作用描述                                         | 可选值或数据类型                                         |
| ---------------- | ------------------------------------------------ | -------------------------------------------------------- |
| `Content-Type`   | 声明响应体中数据的媒体格式（MIME 类型）          | `text/html`、<br />`application/json`、<br />`image/png` |
| `Content-Length` | 声明响应体的字节长度                             | 数字（如 `1024`）                                        |
| `Cache-Control`  | 控制缓存行为，指导客户端或代理服务器如何缓存响应 | `no-cache`、<br />`max-age=3600`、<br />`private`        |
| `Set-Cookie`     | 向客户端设置 Cookie，用于会话管理                | 字符串<br />（如 `session_id=abc123; Path=/; HttpOnly`） |
| `Server`         | 标识处理请求的服务器软件名称及版本               | 字符串（如 `nginx/1.18.0`）                              |

### 空行

响应头和响应体之间必须用一个空行（Blank Line）（即回车换行符 `\r\n\r\n`）进行分隔。这个空行告知服务器头部信息已结束，后续内容为响应体。

### 响应体

响应体（Response Body）位于空行之后，用于携带服务器返回给客户端的实际数据。其具体格式由响应头中的 `Content-Type` 字段决定。

1. HTML 文档

   当 `Content-Type` 为 `text/html` 时，响应体是网页的 HTML 代码。

2. JSON 数据

   当 `Content-Type` 为 `application/json` 时，响应体是结构化的 JSON 字符串。

3. 二进制文件

   当 `Content-Type` 为 `image/png` 或 `application/octet-stream` 时，响应体是图片、视频等二进制数据流。

## 状态码分类

状态码是响应报文中最关键的部分，它决定了客户端后续的处理逻辑。用来表名请求是否完成。

| 状态码分类            | 含义                                 | 典型状态码及说明                                             |
| --------------------- | ------------------------------------ | ------------------------------------------------------------ |
| **1xx（信息性）**     | 请求已接收，正在处理                 | `100 Continue`：客户端应继续发送请求体。                     |
| **2xx（成功）**       | 请求已成功被服务器接收、理解并接受   | `200 OK`：请求成功，响应体包含请求的资源。 <br />`201 Created`：请求成功，新资源已创建。 <br />`204 No Content`：请求成功，但无响应体返回。 |
| **3xx（重定向）**     | 需要客户端采取进一步操作才能完成请求 | `301 Moved Permanently`：资源已永久移动到新 URL。 <br />`302 Found`：资源临时移动到新 URL。 <br />`304 Not Modified`：资源未修改，可使用缓存。 |
| **4xx（客户端错误）** | 请求包含语法错误或无法被服务器理解   | `400 Bad Request`：请求报文存在语法错误。 <br />`401 Unauthorized`：请求需要身份验证。 <br />`403 Forbidden`：服务器拒绝执行此请求。 <br />`404 Not Found`：请求的资源在服务器上不存在。 |
| **5xx（服务器错误）** | 服务器在处理请求时发生错误           | `500 Internal Server Error`：服务器内部发生未预期的错误。 <br />`502 Bad Gateway`：网关或代理服务器从上游服务器收到无效响应。 <br />`503 Service Unavailable`：服务器暂时无法处理请求（如过载或维护）。 |

## 使用

在前端开发中，响应报文通常通过 AJAX 技术（如 `fetch` API 或 `axios` 库）获取。获取到的响应对象包含了状态码、响应头和响应体。

### `fetch`

```javascript
fetch('https://api.example.com/users')
  .then(response => {
    // 1. 获取状态码
    console.log('状态码:', response.status); // 例如：200

    // 2. 获取响应头
    console.log('内容类型:', response.headers.get('Content-Type')); // 例如：application/json

    // 3. 获取响应体（需异步解析）
    return response.json(); 
  })
  .then(data => {
    // 4. 处理解析后的响应体数据
    console.log('用户列表:', data);
  })
  .catch(error => {
    // 捕获网络错误等异常
    console.error('请求失败:', error);
  });
```

### `axios`

```javascript
axios.get('https://api.example.com/users')
  .then(result => {
    // 1. 获取状态码
    console.log('状态码:', result.status); // 例如：200

    // 2. 获取响应头
    console.log('内容类型:', result.headers['content-type']); // 例如：application/json

    // 3. 获取响应体（axios 会自动解析 JSON）
    console.log('用户列表:', result.data);
  })
  .catch(error => {
    // 当状态码超出 2xx 范围时，会进入此分支
    if (error.response) {
      console.log('错误状态码:', error.response.status);
      console.log('错误信息:', error.response.data);
    }
  });
```
