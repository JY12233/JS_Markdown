# 介绍

1. TypeScript 由**微软**开发，是基于 JavaScript 的一个**扩展语言**。
2. TypeScript 包含了 JavaScript 的所有内容，即：TypeScript 是 JavaScript 的**超集**。
3. TypeScript 增加了：静态类型检查、接口、泛型等很多**现代开发特性**，因此更适合**大型项目**的开发。
4. TypeScript 需要**编译**为 JavaScript，然后交给浏览器或其他 **JavaScript 运行环境**执行。

# 环境搭建

## 底层逻辑

TypeScript 无法直接在浏览器或 Node.js 中运行，必须经过编译（Transpile）转换为 JavaScript 才能被执行。因此，搭建 TS 环境的核心本质是配置一套“源码编写 -> 实时编译 -> 运行产物”的标准化工作流。

## 前置依赖

TypeScript 的编译器（`tsc`）本身是一个基于 Node.js 开发的工具。搭建 TS 环境前，必须确保本地已安装 Node.js 及其附带的 npm 包管理器。

- 版本验证

  在终端执行 `node -v` 与 `npm -v`，若能正常输出版本号，则说明前置运行时环境就绪。

- 镜像源配置（推荐）

  为提升后续依赖包的下载速度，建议将 npm 默认源切换为国内镜像（如淘宝镜像）：

    ```bash
    npm config set registry https://registry.npmmirror.com
    ```

## 全局安装

通过 npm 将 TypeScript 编译器全局安装至系统中，以便在任意项目目录下调用 `tsc` 命令。

- 安装命令

    ```bash
    npm install -g typescript
    ```

- 验证安装

  执行 `tsc -v`，成功输出版本号（如 `Version 5.x.x`）即代表编译器安装成功。

## 工程化配置

在实际开发中，TS 环境通常以项目为单位进行隔离配置，而非依赖全局设置。

### 初始化

1. 创建并进入项目目录

    ```bash
    mkdir ts-project && cd ts-project
    ```

1. 初始化 npm 项目（生成 `package.json` 用于管理项目依赖）

    ```bash
    npm init -y
    ```

    > 记得把这个文件里的 `"type": "commonjs"` 换成 `"type": "module"`。

1. 生成 TS 配置文件

    执行以下命令，会在项目根目录生成 `tsconfig.json`。

    ```bash
    tsc --init
    ```

### ts 的 json 文件

```json
{
    // Visit https://aka.ms/tsconfig to read more about this file
    "compilerOptions": {
        // 监视和输出的目录
        "rootDir": "./src/",
        "outDir": "./output",

        // Environment Settings
        // See also https://aka.ms/tsconfig/module
        "module": "nodenext",
        "target": "es2025", // 编译后的代码风格
        "types": [],
        // For nodejs:
        // "lib": ["esnext"],
        // "types": ["node"],
        // and npm install -D @types/node

        // Other Outputs
        // 是否生成对应的类型声明文件
        "sourceMap": false,
        "declaration": false,
        "declarationMap": false,

        // Stricter Typechecking Options
        "noUncheckedIndexedAccess": true,
        "exactOptionalPropertyTypes": true,

        // Style Options
        // "noImplicitReturns": true,
        // "noImplicitOverride": true,
        // "noUnusedLocals": true,
        // "noUnusedParameters": true,
        // "noFallthroughCasesInSwitch": true,
        // "noPropertyAccessFromIndexSignature": true,

        // Recommended Options
        "strict": true,
        "jsx": "react-jsx",
        "verbatimModuleSyntax": false, //? 是否把模块作为什么东西
        "isolatedModules": true,
        "noUncheckedSideEffectImports": true,
        "moduleDetection": "force",
        "skipLibCheck": true,
        "noEmitOnError": true,
        "incremental": true // 编译器会将上次编译的项目信息缓存到 .tsbuildinfo 文件中。
        
        "baseUrl": "./src", // 指定解析非相对模块名的基准目录
        "paths": {
          "@output/*": ["output/*"], // 将 @output/* 映射到 src/output/*
          "@utils/*": ["utils/*"]    // 可配置多个别名
        }
    }
}
```

> **路径解释**
>
> | 配置项     | 作用描述                             | 可选值或说明                              |
> | ---------- | ------------------------------------ | ----------------------------------------- |
> | `baseUrl`  | 设置解析非绝对路径模块名时的基准目录 | 字符串（通常设置为 `./src` 或 `.`）       |
> | `paths`    | 定义路径别名与实际路径的映射关系     | 对象（键为别名模式，值为实际路径数组）    |
> | `*` 通配符 | 匹配别名下的所有子路径与文件         | 键与值中必须同时包含 `*` 才能正确映射目录 |
>
> ```ts
> // 传统相对路径（层级深时极易出错且难以维护）
> import { helper } from '../../../output/helper';
> 
> // 路径别名（简洁直观，移动文件时无需修改路径）
> import { helper } from '@output/helper';
> ```

### 设置监视

设置后会自动编译，手动就 `tsc [文件名]`。

```bash
tsc --watch [文件名] # 不写则监控工作目录下的所有 .ts 文件
```

如果不想在 ts 错误的时候转换，则找到配置中的 `noEmitOnError`，设置为 `true`；也可以在 watch 时添加 `--noEmitOnError`。

### 编译文件处理

这些属性与 `compilerOptions` 同级，指定 `tsc` 指令编译的文件。

| 属性名称  | 作用描述                               | 适用场景                                        |
| --------- | -------------------------------------- | ----------------------------------------------- |
| `files`   | 显式指定需要编译的文件路径列表         | 文件数量极少，需精确控制入口文件                |
| `include` | 通过 glob 模式匹配需要编译的文件或目录 | 文件较多，需按目录或命名规则批量包含            |
| `exclude` | 通过 glob 模式匹配需要排除的文件或目录 | 从 `include` 的结果中剔除特定文件（如测试文件） |

## 核心配置

`tsconfig.json` 是 TypeScript 项目的核心配置文件，用于精确控制编译器的行为。以下是推荐的基础配置及其作用：

| 配置项            | 作用描述                                        | 推荐值/可选值                            |
| ----------------- | ----------------------------------------------- | ---------------------------------------- |
| `target`          | 指定编译后的 JavaScript 目标版本                | `ES6` 或 `ES2020`（适配现代浏览器）      |
| `module`          | 指定生成的模块系统代码规范                      | `CommonJS`（Node.js）或 `ESNext`（前端） |
| `strict`          | 开启所有严格的类型检查选项                      | `true`（强烈推荐，保证代码质量）         |
| `outDir`          | 指定编译后的 JS 文件输出目录                    | `./dist`                                 |
| `rootDir`         | 指定 TS 源码的根目录                            | `./src`                                  |
| `esModuleInterop` | 允许使用 `import x from 'x'` 导入 CommonJS 模块 | `true`                                   |

## 编辑器工作流

Visual Studio Code 内置了 TypeScript 语言服务，无需安装额外插件即可提供开箱即用的开发体验。

- 智能提示

  VS Code 能够自动识别 `.ts` 文件，并提供实时的类型检查、代码补全与跳转功能。

- 编译工作流

  在终端执行 `tsc --watch`（监听模式），编译器会根据 `tsconfig.json` 的配置，实时监控 `src` 目录下的 `.ts` 文件变动，并自动将其编译为 `dist` 目录下的 `.js` 文件。

```cmd

npm : File D:/Coding/NodeJS/npm.ps1 cannot be loaded because running scripts is disabled on this system. For more infor
```

Windows PowerShell 默认的执行策略（Execution Policy）为 `Restricted`，该策略会禁止运行任何脚本文件（包括 npm 的启动脚本 `npm.ps1`），以防止潜在的恶意脚本执行。

以管理员身份运行 PowerShell，并执行以下命令来更改执行策略：

1. **打开管理员权限的 PowerShell**

2. **执行策略更改命令** 

   在打开的窗口中输入以下命令并按回车：

   ```powershell
   Set-ExecutionPolicy RemoteSigned
   ```

   当系统提示确认时，输入 `Y` 并按回车。

3. **验证更改** 
   关闭并重新打开一个新的 PowerShell 窗口（无需管理员权限），再次输入 `npm -v`，若能正常显示版本号，则说明问题已解决。

> **策略说明**
>
> - `RemoteSigned`
>
>   允许运行本地创建的脚本，但要求从互联网下载的脚本必须经过受信任的发布者签名。这是兼顾安全与开发需求的推荐设置。
>
> - `Restricted`
>
>   默认策略，不允许运行任何脚本。
>
> - `Unrestricted`
>
>   允许运行所有脚本，但会带来安全风险，不推荐使用。

### 创建文件夹
打开 Node.js 安装目录，新建两个文件夹：
- `node_global` — 存放全局安装的模块
- `node_cache` — 存放 npm 缓存

> 直接在 vs code 的终端中打开使用 npm 下载到工作目录时，会因为权限不足导致无法下载。可以采用下面的步骤：
>
> 1. 在文件资源管理器中找到刚刚创建的 `node_cache` 文件夹。
> 2. 右键点击该文件夹，选择“属性”。
> 3. 切换到“安全”选项卡。
> 4. 选中当前用户，点击“编辑”，在权限列表中勾选“完全控制”。
> 5. 点击“确定”保存更改。

### 配置 npm 路径
以**管理员身份**打开命令提示符，输入以下命令（将路径替换为实际路径）：

```bash
npm config set prefix "你的路径\node_global"
npm config set cache "你的路径\node_cache"
```

**示例**（假设安装路径为 `E:\nodejs`）：

```bash
npm config set prefix "E:\nodejs\node_global"
npm config set cache "E:\nodejs\node_cache"
```

**验证配置是否成功**：

```bash
npm config get prefix
npm config get cache
```

> **注意事项**
>
> - 确保路径正确，建议直接复制文件夹路径。
> - 如果提示权限不足，请确认已使用管理员身份运行。

### 配置环境变量

1. 新建**系统**变量 `NODE_PATH`：

   1. 右键点击 **此电脑** -> **属性** -> **高级系统设置** -> **环境变量**。

   2. 在 **系统变量** 区域点击 **新建**。

   3. 变量名：`NODE_PATH`。

   4. 变量值：`E:\nodejs\node_global\node_modules`（即 `node_global` 路径后追加 `\node_modules`）。
2. 修改**用户**变量 Path
   1. 在 **用户变量** 区域选择 `Path`，点击 **编辑**。
   2. 将默认的 `C:\Users\你的用户名\AppData\Roaming\npm` 修改为 `node_global` 文件夹路径（如 `E:\nodejs\node_global`）。
3. 更新系统变量 Path
   1. 在 **系统变量** 区域选择 `Path`，点击 **编辑**。
   2. 点击 **新建**，输入 `%NODE_PATH%`，依次点击确定关闭所有窗口。
4. 验证环境变量配置

    ```bash
    echo %NODE_PATH%
    ```

    如果输出正确路径（如 `E:\nodejs\node_global\node_modules`），说明配置成功。

| 变量名称           | 作用描述                 | 配置要点                                                     |
| ------------------ | ------------------------ | ------------------------------------------------------------ |
| `NODE_PATH`        | 指定全局模块的查找路径   | 指向 `node_global\node_modules`，<br />确保 Node.js 运行时能找到全局安装的包。 |
| `Path`（用户变量） | 指定可执行文件的搜索路径 | 指向 `node_global` 文件夹，<br />确保在任意终端都能直接运行全局安装的命令（如 `tsc`、`vue`）。 |
| `Path`（系统变量） | 补充系统级模块查找路径   | 添加 `%NODE_PATH%`，使系统级进程也能正确解析全局模块。       |

# 编译文件处理

默认配置下，使用 `tsc` 编译会出现 `.d.ts`、`.d.ts.map`、`.js.map` 这三个另外的文件。

出现这些额外文件，是因为在 `tsconfig.json` 里**开启了对应的编译选项**。它们不是错误，而是 TypeScript 提供的高级功能产物。

## `.js.map`

这是一个**源码映射（Source Map）**文件。

它记录了编译后的 `ex.js` 代码与原始 `ex.ts` 代码的**对应关系**（行号、列号）。

**调试时**，浏览器或 Node.js 的调试工具会自动读取它。打断点时，看到的是可读的 TypeScript 源码，而不是被编译后晦涩的 `"use strict";` 和 `Object.defineProperty`。

## `.d.ts`

这是一个**类型声明文件（Type Declaration）**。

它只包含类型信息（变量、函数、类的类型签名），不包含具体的逻辑实现。

如果这个项目是一个**库（npm 包）**，别人用 TypeScript 导入这个项目时，TS 编译器会依靠这个 `.d.ts` 文件进行**类型检查**和**智能提示**，而无需看到项目源码。

## `.d.ts.map`

这是一个**声明文件的源码映射**。

它把 `.d.ts` 里的类型定义位置，映射回原始的 `.ts` 源码位置。

**对库的消费者来说**，当他们在 VSCode 中按住 `Ctrl`（或 `Cmd`）点击导出的函数名，选择“转到定义（Go to Definition）”时，编辑器会直接跳转到**原始 `.ts` 源文件**（而不是显示冷冰冰的 `.d.ts` 空壳），极大提升了阅读源码的体验。

## 去掉

如果暂时用不上它们，可以在 `tsconfig.json` 中把这三个选项设为 `false` 或直接删掉：

```json
"sourceMap": false,
"declaration": false,
"declarationMap": false
```

但如果这个项目是用来给别人引用的库，**建议保留** `.d.ts` 和 `.d.ts.map`；如果需要调试 TS 源码，**建议保留** `.js.map`。

# 生成的 js 文件风格

`package.json` 中的 `type` 字段是 Node.js 的模块系统全局开关，决定了项目中 `.js` 文件的默认解析规范。

## 对比

| 对比维度            | `"type": "commonjs"` (默认)    | `"type": "module"`                 |
| ------------------- | ------------------------------ | ---------------------------------- |
| **模块规范**        | CommonJS (CJS)                 | ES Modules (ESM)                   |
| **导入语法**        | `const x = require('x')`       | `import x from 'x'`                |
| **导出语法**        | `module.exports = {}`          | `export default {}` / `export {}`  |
| **`.js` 文件解析**  | 视为 CommonJS 模块             | 视为 ES Module                     |
| **`.cjs` 文件解析** | 强制视为 CommonJS              | 强制视为 CommonJS                  |
| **`.mjs` 文件解析** | 强制视为 ES Module             | 强制视为 ES Module                 |
| **全局变量支持**    | 支持 `__dirname`, `__filename` | 不支持（需使用 `import.meta.url`） |

## 语法成分

| 配置值       | 作用描述                                                     | 典型使用场景                                                 |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `"commonjs"` | Node.js 的默认模块系统。<br />所有 `.js` 文件按 CJS 规范解析，支持 `require` 和 `module.exports`。 | 传统的 Node.js 后端项目、旧版遗留代码、不需要打包工具直接运行的脚本。 |
| `"module"`   | 现代 JavaScript 标准模块系统。<br />所有 `.js` 文件按 ESM 规范解析，支持 `import` 和 `export`。 | 现代前端项目（配合 Vite/Webpack）、现代 Node.js 应用、发布支持 Tree Shaking 的 NPM 包。 |

## 注意事项

- 文件扩展名的强制覆盖

  无论 `type` 字段如何设置，`.cjs` 文件永远被视为 CommonJS，`.mjs` 文件永远被视为 ES Module。

- 配置文件的兼容性陷阱

  当设置为 `"type": "module"` 时，项目中的配置文件（如 `.eslintrc.js`、`babel.config.js`）若仍使用 `module.exports` 语法，Node.js 会报错。解决办法是将这些配置文件重命名为 `.cjs` 后缀（如 `.eslintrc.cjs`）。

- NPM 初始化默认值

  执行 `npm init -y` 时，默认生成的 `package.json` 不包含 `type` 字段（即默认为 CommonJS）。若需使用 ESM，需手动添加 `"type": "module"` 或使用 `npm pkg set type=module` 命令。

## 代码示例

### CommonJS
